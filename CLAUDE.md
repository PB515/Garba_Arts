## What this is

An admin/CRM tool for **The Garba Arts**, a garba dance class with 2 locations (Aliya, Sportsclub) and 6 batches. Replaces an Excel sheet for tracking inquiries/leads (from WhatsApp, Instagram, referrals, or walk-ins), demo attendance, enrollment status, and fee payments (cash/UPI, often partial/split), plus event registration and a Navratri pass proof-of-concept. Two staff roles: `super_admin` (owner + family, sees everything merged) and `location_admin` (full CRUD within exactly one location, zero access to the other). One deliberate public page (`/navratri`, no login) — everything else stays staff-only. Full context: [`docs/discovery-brief.md`](docs/discovery-brief.md), [`docs/app-prd.md`](docs/app-prd.md).

Defaults to today on the add form but stays editable for backdating a late-logged lead. Owner confirmed this is one field with one meaning, not two separate dates.

24. **Neither event registration nor the Navratri pass system needs a payment gateway.** Confirmed directly: "money and stuff will be just logged here, not collected" — same spirit as student fees. Both `amount_paid` columns are plain staff-entered numbers, not payment-processor integrations.
25. **`/navratri` is a real, deliberate exception to "zero client/student-facing pages" (decision #1) — the one public, no-login page in this entire build.** Confirmed directly: it's genuine public self-service (a group representative registers themselves), not admin-entered. Kept intentionally minimal per the owner ("just buttons and some tabs... proving the method") since there's ~2.5 months of runway before it needs to be real. Real dates/prices are explicit placeholders (`lib/navratri-config.ts`) — the owner said those get decided 1-2 weeks before Navratri, not now.
26. **The public write never gets a direct `anon` RLS grant — it goes through a server action using the service-role client instead.** This is the key security property: the price is computed server-side from the trusted clock, so nobody can submit their own price via a raw API call. `anon` has zero grants on `navratri_registrations`, same as every other table — decision #12 is fully preserved, not weakened, even though there's now a real public form. Proven both directions in `verify-denial.ts`: the public page works logged-out (tested live), and a direct anon API call to the same table is still refused.
27. **Two roles: `super_admin` (owner + family, merged view) and `location_admin` (exactly one location, full CRUD within it, zero access to any other).** Reverses decision #10. `staff_roles` table + `is_super_admin()`/`staff_location_id()` `SECURITY DEFINER` helpers, same pattern as the IDP's `has_role.sql`. Only `students`/`payments` are location-scoped — `locations`/`batches` stay flat (low-sensitivity lookup data), and `events`/`event_registrations`/`navratri_registrations` are explicitly **not yet scoped** — the owner said "need to verify first" rather than confirming either way. Role assignment happens only via `tooling/create-account.ts` (service-role), never through the app. → `docs/data-model-security.md`, `docs/app-prd.md`
28. **Combined fee data (`/fees`, CSV export) is `super_admin`-only; an individual student's own fee numbers stay visible to that location's admin.** "Individual fees ok, combined fees restricted" is an app-level rule (a route check), not something RLS alone can express — RLS naturally distinguishes *locations* from each other, not "your own location's total" from "everyone's total" within one location. CSV export was restricted proactively (not explicitly asked) because it's just as much a "combined" view as `/fees` and would otherwise be a loophole around the same stated rule. → `docs/app-prd.md`
29. **The Dashboard shows zero money, for any role.** Not a role restriction — there's simply no rupee figure on it anymore, for anyone. Only list-level simplification (Joined tab's Paid/Not Paid/Half Paid badge) plus the individual student page's real numbers remain outside the super-admin-only Fees tab.
30. **Status collapses again, from 6 values (decision #21's `inquiry_date` era) to 3: `follow_up` (yellow, "ask again"), `dropped` (red), `joined` (green).** A record is never removed from the Inquiry list once created — permanent historical log, e.g. "everyone who inquired in 2026, whatever happened to them." Marking someone `joined` doesn't move them, it makes them *also* appear in the new Joined tab. The "why" behind a dropped lead (took the demo vs. never did vs. went cold immediately) lives in `remarks`, not more status values — confirmed directly rather than adding a `demo_taken` boolean.
31. **A small, separate demo-lecture fee** (`students.demo_fee_amount`/`demo_fee_paid`) — independent of the main course `fee_total`, independent of outcome (charged whether the lead ends up joined or dropped). Visible only in the super-admin Fees tab alongside the main tally, since it's still money.
32. **Two security gates now, not one.** `verify-denial.ts` (anon vs. authenticated) and `verify-location-denial.ts` (location_admin vs. location_admin, added with the role split) — proven with real signed-in test accounts, not just trusted from the RLS policy text. Both must pass before any feature touching `students`/`payments` ships. → `docs/data-model-security.md`
33. **The batch dropdown must be empty/disabled until a location is picked, not fall back to showing every batch merged.** Found from a user-supplied screenshot, not guessed — batch names repeat across locations, so an unfiltered list is genuinely ambiguous (two identical "10-11 PM" options), not just untidy. Applies to every use of `location-batch-select.tsx` (add form, filter, edit form) uniformly.
34. **`students.whatsapp_number` is its own field, separate from `phone_number`.** Confirmed directly: "some people have 2" — a different number for calls vs. WhatsApp.
35. **Payments splitting cash+UPI in one sitting log as a single entry with `mode = 'cash_upi'`, not two separate rows.** The owner's explicit preference over the two-line-item approach originally proposed — simpler, one entry per real-world payment event.
36. **`referred_by` generalized into `source_detail`, shown for any source, not just Referral.** Owner: "I want same for others as we can also know source of others." One generic optional field (which Instagram post, which WhatsApp group, who spoke to them at a walk-in), not a different field per source — matches the "more simple is more usable" preference stated for the earlier Inquiry/Joined redesign.
37. **Events get a second write path: per-event opt-in public self-registration (`/events/[id]/register`, off by default), alongside the existing admin-entered path.** Confirmed directly, and confirmed it applies everywhere: replace the friend-count with actual attendee *names*, both for public and admin-entered registrations — "we don't just want number coming with student but also who are coming, number and name." Same security pattern as `/navratri` (server action + service-role, never a direct anon RLS grant) for the same underlying reason: never trust a public form's own account of the world, re-check `public_registration_enabled` server-side.
38. **`event_registrations.friend_count` is gone, replaced by counting `event_attendees` rows — a single source of truth instead of a number that could drift from the actual names.** Existing demo-seeded registrations lost their friend counts in the migration (no way to invent names for previously-uncounted friends) — acceptable since it's demo data, not real data; noted so it isn't mistaken for a bug later.
39. **The Fees tab's breakdown (payment mode / location / batch) is always computed from the full, unfiltered dataset; the location/batch/mode filters only narrow the payment-log table underneath.** Confirmed directly ("so can see what type of payment come how much... them demo lecture then fees then aliya total... 8 to 9 total all") — the ask was every slice visible at once, not one slice at a time behind a filter. Verified live: all three breakdowns' "All" rows reconcile to the same `totalCollected` figure.
40. **A Cash+UPI split payment stores the real split (`payments.cash_amount`/`upi_amount`), not just a combined total — the Fees tab reconciles "Total Cash"/"Total UPI" (decomposed, split payments counted into both) separately from "Collected by payment mode" (Cash/UPI/Cash+UPI as logged, split payments in their own bucket).** Confirmed directly: "How we got money is Cash, UPI and cash+UPI" (keep the existing three-way log-mode breakdown) vs. "Total cash, and total upi for Money" (a true reconciliation figure — Total Cash + Total UPI must always equal Total collected). Two different questions, two separate sections, neither replaces the other. Verified live: 30800 (cash) + 40200 (upi) = 71000 (total collected), exactly.
41. **Marking someone "Joined" from the Inquiry list's quick-set buttons asks for confirmation first ("Mark [Name] as Joined? They'll move to the Joined tab."); the other two statuses (Ask again, Dropped) stay instant, unchanged.** Confirmed directly: the owner pointed out there was no visible "this is happening now" moment when converting an inquiry to a joined student, and wanted a pop-up explaining what's about to happen before it happens — since marking someone joined is the one status change that's easy to miss/repeat without noticing. `status-quick-set.tsx` (new client component) owns this; `setStudentStatus` itself is unchanged (already idempotent — the confirmation is a UX safeguard, not a data-integrity one).
42. **Pending fees on the Joined tab are surfaced two ways: a light red/yellow tint on the whole row (Not Paid/Half Paid), and a "Pending fees only" checkbox filter — both in-app/visual, deliberately not an active notification system (no SMS/email/push).** Given a multi-choice question, the owner picked both the row highlight and the filter, not the third option offered (a Dashboard pending-fees count) — kept off the Dashboard, consistent with decision #29 (zero money/fee signals there, for any role). Fee status is derived (needs a payments join), so the filter is applied in JS after computing each row's status, not as a SQL `where` clause.
43. **The Joined tab's filter form is keyed on its own search params (`key={JSON.stringify(params)}`), so "Reset filters" forces a remount instead of leaving stale UI.** Found live, not guessed: clicking a plain `<Link href="/students/joined">` correctly cleared the URL and the data (23 rows, unfiltered), but the checkbox and location `<select>` kept showing their old checked/selected state, since Next.js's soft client-side navigation re-renders the form with new server data without resetting uncontrolled DOM state (`defaultChecked`/a child client component's own `useState`). The `key` forces React to unmount+remount the whole form (and `LocationBatchSelect` inside it) on any params change, which reapplies every field's initial state fresh. Same fix would apply to any future filter form that gains a "reset" link.
44. **Every field where a person types their own name says "Full Name" (or "Your full name"/"Registrant full name" in context), not the bare word "Name."** Confirmed directly, and confirmed it applies everywhere a person's name is collected, not just the one field pointed at: the Add inquiry form, the student edit page, the admin "Add registration" form's registrant field, the public event-registration page, and the Navratri page. Deliberately left alone: the Event name field (that names the event, not a person) and table column headers (labels, not input boxes).
45. **A full "is what we built actually correct" audit found two real bugs and one validation gap, all now fixed; a third finding (a latent Cash+UPI reconciliation risk) was left as a documented risk, not fixed, since it's unreachable through the app as built.** See Build Log Phase 9's audit entry for the full list. The owner's response was explicit: fix what's clearly broken now, and they'll separately give direction on the deferred items (including the event-registration edit gap).
46. **The Cash+UPI null-split risk (decision #45) is now closed at the database level, not just documented.** `payments_cash_upi_split_check` (added `0014_payments_cash_upi_split_check.sql`) makes it structurally impossible to save a `cash_upi` row with a missing split or a split that doesn't sum to `amount` — enforced by Postgres itself, so it holds even against a future Excel import or a manual SQL fix, not just the current app's own validation. Verified live: a null-split insert and a mismatched-sum insert were both rejected directly against the database (bypassing the app entirely, via service-role), a correctly-split row still succeeds.
47. **Events get real location-scoping, resolving the long-open item from decision #27 — but on the registration, not the event itself.** The owner, across two rounds: an event's own venue is irrelevant (it can happen at a party plot, not tied to Aliya/Sportsclub), what matters is how many registrants came from each location. So `events` stays unscoped, but `event_registrations` gained a `location_id` (`0015_event_registration_location_scoping.sql`), RLS-scoped the same way `payments` scopes through `students` — `event_attendees` inherits scoping via its parent `registration_id`. `location_id` is nullable at the database level specifically so a public self-registration (`/events/[id]/register`) stays unattributed: a `location_id = staff_location_id()` comparison is never true against `null`, so an unattributed row is automatically invisible to every `location_admin` and visible only to `super_admin` — no special-casing needed, it falls straight out of the RLS policy. Admin-entered registrations require a location at the app level (`createRegistration` throws without one); the public form itself is unchanged, deliberately not asking a stranger which of the two dance-class locations they're affiliated with. The event detail page gained a "Registered by location" breakdown (super_admin only, including an "Unattributed (public)" row so the numbers visibly reconcile to the combined total) — a `location_admin`'s existing combined summary needed no change at all, since RLS already narrows their registrations list to their own location. `tooling/verify-location-denial.ts` extended with 9 new checks proving this live with real signed-in accounts (own-location visibility, cross-location denial both ways, unattributed invisible to both admins but visible to super_admin, cross-location write denial, attendee inheritance) — same rigor as every prior location-scoping change.
48. **Event registrations are now editable in place (decision #5's Path A, from the audit).** `RegistrationEditRow` (new client component) toggles a registration row into an inline form, wired to the already-correct `updateRegistration`, which now also requires `location_id` (matching `createRegistration`). One real consequence worth naming: since editing requires a location the same way creating does, there's no way to move a registration *back* to unattributed/public through the app once it has a location — only a genuine public self-registration stays unattributed. That's an intentional, not accidental, side effect of reusing the same required-field validation for both create and edit.
49. **CSV export now exists on Inquiry and Fees, and the Joined tab's existing button got fixed, not just copied.** The Joined tab's "Export CSV" was a static link that silently ignored the tab's own filters — fixed to carry `q`/`location`/`batch`/`pending` plus a hardcoded `status=joined`. Inquiry reuses the same `/api/export/students` route (now also supporting a `pending` param, computed the same way the Joined page itself computes it — fee status is derived, not a stored column). Fees is a payment log, not a student roster, so it got its own new route, `/api/export/payments` (same double-gated `super_admin`-only pattern as the existing route), exporting one row per payment filtered by `location`/`batch`/`mode`, matching the "All payments" table exactly. `buildQueryString()` (new, `lib/form.ts`) carries each page's current filters into its export link.
