## What this is

An admin/CRM tool for **The Garba Arts**, a garba dance class with 2 locations (Aalay, Sportsclub) and 6 batches. Replaces an Excel sheet for tracking inquiries/leads (from WhatsApp, Instagram, referrals, or walk-ins), demo attendance, enrollment status, and fee payments (cash/UPI, often partial/split), plus event registration and a Navratri pass proof-of-concept. Two staff roles: `super_admin` (owner + family, sees everything merged) and `location_admin` (full CRUD within exactly one location, zero access to the other). One deliberate public page (`/navratri`, no login) — everything else stays staff-only. Full context: [`docs/discovery-brief.md`](docs/discovery-brief.md), [`docs/app-prd.md`](docs/app-prd.md).

42. **Pending fees on the Joined tab are surfaced two ways: a light red/yellow tint on the whole row (Not Paid/Half Paid), and a "Pending fees only" checkbox filter — both in-app/visual, deliberately not an active notification system (no SMS/email/push).** Given a multi-choice question, the owner picked both the row highlight and the filter, not the third option offered (a Dashboard pending-fees count) — kept off the Dashboard, consistent with decision #29 (zero money/fee signals there, for any role). 46. **The Cash+UPI null-split risk (decision #45) is now closed at the database level, not just documented.** `payments_cash_upi_split_check` (added `0014_payments_cash_upi_split_check.sql`) makes it structurally impossible to save a `cash_upi` row with a missing split or a split that doesn't sum to `amount` — enforced by Postgres itself, so it holds even against a future Excel import or a manual SQL fix, not just the current app's own validation. Verified live: a null-split insert and a mismatched-sum insert were both rejected directly against the database (bypassing the app entirely, via service-role), a correctly-split row still succeeds.
